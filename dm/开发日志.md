# 学习路径模块开发日志

## 项目背景

基于 MediCraft（AI学习辅助系统）前后端项目，为学习路径规划模块生成完整的后端代码。
- 后端：Spring Boot 3.3.5 + MyBatis-Plus + Spring AI + MySQL + Redis
- 前端：Vue 3 + Element Plus + Pinia + Axios

---

## 第一阶段：需求分析与代码生成

### 任务
根据前端学习路径页面（5个Vue组件、8个API接口）和需求分析文档，生成对应的后端Java代码。

### 做了什么
1. 读取 `前端.txt`、`需求分析.txt` 理解业务模块划分
2. 扫描前端 `Media-edu` 项目，找到学习路径模块的所有文件：
   - `src/api/learningPath.js` — 8个REST接口定义
   - `src/stores/learningPath.js` — Pinia状态管理
   - `src/views/learning-path/` — 5个页面组件
3. 扫描后端 `MediCraft` 项目，理解现有代码规范：
   - 实体类：`@Data` + `@TableName` + `@TableId(IdType.AUTO)` + `@TableLogic`
   - 控制器：`@RestController` + 返回 `Result<T>`
   - 服务层：接口继承 `IService`，实现继承 `ServiceImpl`
   - 响应封装：`Result.success(data)` / `Result.fail(code, msg)`
   - 用户上下文：`BaseContext.getCurrentId()` 获取当前登录用户ID

### 生成的文件（15个）
- **SQL**：`learning_path_schema.sql`（4张表）
- **VO类**（7个）：`GeneratePathVO`、`CompleteStepVO`、`AdjustPathVO`、`RecordBehaviorVO`、`LearningPathDetailVO`、`LearningPathStepVO`、`RecommendedResourceVO`
- **Mapper**（4个）：`LearningPathMapper`、`LearningPathStepMapper`、`LearningPathStepResourceMapper`、`LearningBehaviorMapper`
- **Service**（2个）：`LearningPathService`（接口）、`LearningPathServiceImpl`（实现）
- **Controller**（1个）：`LearningPathController`

## 第二阶段：SQL Schema 冲突修复

### 遇到的错误
用户提供了已有的 `MediCraft.sql` 文件，我生成的SQL与之存在多处冲突。

### 具体冲突点
| 字段 | 我生成的 | 实际SQL | 问题 |
|------|---------|---------|------|
| `learning_path.status` | `pending/inProgress/completed/paused` (4态) | `doing/finish` (2态) | 状态值完全不同 |
| `learning_path_step.finish_status` | `int 0/1/2` (3态) | `tinyint 0/1` (2态) | 多了一个中间态 |
| `learning_behavior` | 有 `create_time` 字段 | 无 `create_time` | 多了字段 |
| `learning_path_step_resource` | 无 `UNIQUE` 约束 | 有 `UNIQUE KEY uk_step_resource` | 缺少约束 |

### 解决方案
1. 用 `MediCraft.sql` 中的表定义覆盖生成的SQL
2. 修改Java代码适配实际数据库：
   - 数据库存 `doing/finish`，VO层映射到前端 `pending/inProgress/completed`
   - 数据库存 `finish_status` 的 `0/1`，VO层根据"是否第一个未完成步骤"推导出 `inProgress`

### 状态映射逻辑
```
数据库 doing  +  有已完成步骤  →  前端 inProgress
数据库 doing  +  无已完成步骤  →  前端 pending
数据库 finish  →  前端 completed

步骤 finish_status=1  →  前端 completed
步骤 finish_status=0 + 是第一个未完成  →  前端 inProgress
步骤 finish_status=0 + 非第一个  →  前端 pending
```

### 涉及的逻辑
**适配层映射（Anti-Corruption Layer）**：数据库用简化的两态设计，前端需要三态展示。不在数据库加字段，而是在Service的VO转换方法 `convertToStepVOs()` 中通过排序位置推导中间态。

## 第三阶段：前端数据不显示问题排查

### 遇到的错误
数据库有4条 `learning_path` 记录，但前端"我的学习路径"页面显示"暂无学习路径"。

### 排查过程

**根因1：Store赋值链路断裂**
- 后端返回结构：`{code: 200, msg: "操作成功", data: {records: [...], total: 4}}`
- Axios响应拦截器（`request.js` 第39-57行）返回 `response.data`，即整个Result对象
- 所以 `response = {code: 200, data: {records: [...], total: 4}}`
- Store代码：`paths.value = response.data` → 赋值为 `{records: [...], total: 4}`（对象，不是数组）
- 模板 `v-for="path in paths"` 遍历对象 → 不报错但不渲染

**根因2：模板用的是mockPaths而非store数据**
- `PathListView.vue` 模板中 `v-for="path in mockPaths"` 引用本地假数据
- `mockPaths` 初始为空数组 `ref([])`，`onMounted` 时 store 的 `getPaths()` 写入了 `paths` 但模板没有读取

**根因3：字段名不匹配**
- 后端VO返回 `pathName` 字段
- 前端删除确认弹窗用 `path.title`，PathListView多处用 `path.title`、`path.totalSteps`、`path.createdAt`
- 这些字段后端都没返回，前端拿到 `undefined`

### 解决方案
1. **修复Store**：`paths.value = response.data.records`，加数组类型校验
2. **修复PathListView**：删除 `mockPaths`，改用 `computed` 从 store 取数据；字段兼容 `path.title || path.pathName`
3. **修复VO**：`LearningPathDetailVO` 添加 `@JsonProperty("title")`、`@JsonProperty("totalSteps")`、`@JsonProperty("createdAt")` 别名getter
4. **同步修复PathStepView、ResourceRecommendView、PathAdjustView**：全部从硬编码mock数据改为从store取真实数据

### 涉及的逻辑
**Axios响应拦截器链路**：理解 `axios.create()` → `interceptors.response.use()` → `return res` 的数据流向。`res` 是 `response.data`（即后端的Result对象），不是axios的原始response。前端store需要 `response.data.records` 才能拿到分页数组。

**Pinia Store 数据流**：`API调用 → axios拦截器 → store action赋值 → computed派生 → template渲染`，任何一环断了都不报错但页面空白。

## 第四阶段：路径调整功能增强

### 任务
完善5种调整类型的前端交互，让每种类型有独立的操作界面。

### 做了什么
1. **延长/压缩周期**：添加时间选项卡片（+1天/+5天/+7天/+2周/+1个月），选中后通过 `params` 字段传给后端
2. **调整顺序**：加载当前路径步骤列表，每个步骤显示序号+名称+描述，右侧4个按钮（置顶/上移/下移/置底）
3. **新增内容**：点击按钮弹出 `el-dialog`，填写知识点名称+详细描述，确认后显示预览标签
4. **简化内容**：点击按钮弹出 `el-dialog`，checkbox列表勾选要删除的步骤

### 后端适配
重写 `adjustPath()` 方法，按类型分流处理：
- `extend/compress`：解析 `params.duration`，用AI根据指定时长重新生成未完成步骤
- `reorder`：直接解析 `params.steps[{id, sort}]` 更新数据库排序，不调AI
- `add`：解析 `params.contentName/contentDetail`，用AI生成2-3个新步骤插入
- `remove`：解析 `params.removeStepIds`，软删除选中步骤，重新编号

### 遇到的错误
**Vue Options API 与 `<script setup>` 混用问题**
- `reasonPlaceholder` 计算属性写在了 Options API 的 `<script>` 块中
- 使用了 `this.adjustType`，但 `adjustType` 定义在 `<script setup>` 中
- `this` 在 Options API 中无法访问 `<script setup>` 的响应式变量

### 解决方案
将 `reasonPlaceholder` 移到 `<script setup>` 中作为 `computed()`，`<script>` 块只保留组件注册。

### 涉及的逻辑
**Vue 3 双script块的作用域隔离**：`<script setup>` 和普通 `<script>` 是两个独立作用域。`<script setup>` 中的变量对 `<script>` 中的 `this` 不可见。需要组件注册时用普通 `<script>` 导出 `components`，逻辑全部放 `<script setup>`。

## 第七阶段：资源推荐模块完善

### 问题描述
资源推荐页面（ResourceRecommendView）打开后始终显示"暂无推荐资源"，即使数据库中有学习资源。

### 排查过程

**根因1：页面依赖URL参数 pathId，但菜单导航不传参数**
```javascript
// 旧代码：只在 pathId 存在时才加载
onMounted(async () => {
  const pathId = route.query.pathId
  if (pathId) {                           // ← 从菜单进入时 pathId 为 undefined
    await learningPathStore.getRecommendedResources(pathId)
  }
  // 没有 else 分支 → 什么都不加载 → 显示空状态
})
```
从侧边栏菜单点击"资源推荐"时，URL是 `/recommend/resource`，没有 `?pathId=xxx`，所以数据永远不会加载。

**根因2：资源类型常量引用可能崩溃**
ResourceRecommendView 引用了 `RESOURCE_TYPES`，如果 constants 文件未正确导出会导致整个页面白屏。

**根因3：空状态信息不友好**
没有区分"没有路径"和"没有资源"两种空状态。

### 解决方案

**方案1：添加路径选择器（dropdown）**
在页面顶部增加 `el-select`，让用户手动选择要推荐资源的路径。逻辑流程：
```
onMounted → 加载路径列表 → 默认选中第一个 → watch(selectedPathId) → 触发加载推荐
```

```javascript
// 新代码：两种方式都能触发加载
watch(selectedPathId, async (newId) => {
  if (newId) {
    await loadRecommendations(newId)
  }
})

onMounted(async () => {
  // 优先用URL参数，其次默认选中第一个路径
  const queryPathId = router.currentRoute.value.query.pathId
  if (queryPathId) {
    selectedPathId.value = String(queryPathId)
  } else if (pathList.value.length > 0) {
    selectedPathId.value = String(pathList.value[0].id)
  }
})
```

**方案2：本地定义 typeConfig 兜底**
```javascript
// 即使 RESOURCE_TYPES 导入失败，也有本地兜底
const typeConfig = {
  document: { label: '文档', icon: 'Document', color: '#67C23a' },
  mindmap: { label: '思维导图', icon: 'Share', color: '#E6A23C' },
  // ...
}
const getTypeConfig = (type) => {
  return RESOURCE_TYPES?.[type] || typeConfig[type] || typeConfig.document
}
```

**方案3：区分空状态**
- 没有路径 → 提示"请先创建学习路径"
- 有路径但没资源 → 提示"请先通过智能体生成资源"

### 涉及的逻辑
**watch + onMounted 协同**：`onMounted` 负责初始化（加载路径列表、设置默认值），`watch` 负责响应变化（用户切换路径时重新加载推荐）。两者配合确保无论哪种进入方式都能正确加载数据。

## 第八阶段：路径调整报错排查与修复

### 问题描述
用户在路径调整页面选择调整类型并提交后，显示"路径调整失败，请重试"。

### 排查过程

**根因1：错误信息被吞掉**
旧的 catch 块只显示固定文案，没有暴露后端具体报错：
```javascript
// 旧代码：无论什么错误都显示同一句话
catch (error) {
  ElMessage.error('路径调整失败，请重试')  // ← 用户看不到真正原因
}
```

**根因2：Store 中 completeStep 的本地更新不可靠**
旧代码尝试在前端手动更新步骤状态，但不更新路径进度和状态：
```javascript
// 旧代码：只改了步骤状态，没改路径进度
const stepIndex = currentSteps.value.findIndex(s => s.id === stepId)
currentSteps.value[stepIndex].status = 'completed'
// 缺少：路径 progress、completedSteps 的更新
```

**根因3：Store 中 getRecommendedResources 未做类型校验**
```javascript
// 旧代码：直接赋值，如果后端返回非数组会崩溃
recommendedResources.value = response.data  // 如果是 null/对象，v-for 会报错
```

### 解决方案

**方案1：前端错误信息透传**
```javascript
// 新代码：提取后端返回的具体错误
catch (error) {
  const msg = error?.response?.data?.msg     // 后端 Result.fail 的 msg
      || error?.response?.data?.message      // HTTP 错误的 message
      || error?.message                      // JS 异常的 message
      || '路径调整失败，请重试'               // 兜底
  console.error('[PathAdjust] 调整失败详情:', error)  // 控制台打印完整堆栈
  ElMessage.error(msg)
}
```

**方案2：completeStep 改为重新获取详情**
```javascript
// 新代码：打卡后直接重新请求后端获取最新数据
async function completeStep(stepId, data = {}) {
  const response = await learningPathApi.completeStep(stepId, data)
  // 刷新当前路径详情以获取最新进度
  if (currentPath.value && currentPath.value.id) {
    await getPathDetail(currentPath.value.id)  // ← 重新请求，数据最准确
  }
  return response
}
```
**为什么这样做**：前端手动维护状态容易出错（需要同时更新步骤状态、路径进度、completedSteps、路径status）。直接重新请求后端，由后端计算所有状态，数据一致性最好。

**方案3：推荐资源加数组校验**
```javascript
recommendedResources.value = Array.isArray(response.data) ? response.data : []
```

### 后端推荐逻辑增强
原有逻辑只查询 `resourceIds` 关联的资源，未关联时随机返回10条。增强后：
1. 优先返回路径步骤直接关联的资源（`resourceIds` 字段），匹配度+25分
2. 资源不足5条时，自动从用户其他资源中补充
3. 推荐理由更具体：关联资源显示"与步骤直接关联"，知识点资源显示具体知识点名称

### 涉及的逻辑
**防御性编程**：前端对后端返回数据做 `Array.isArray()` 校验，防止 null/对象导致模板 `v-for` 崩溃。

**数据一致性原则**：涉及多表更新的操作（打卡=更新步骤+更新路径+记录行为），前端不应手动拼凑状态，应该重新请求后端获取完整最新数据。

**错误信息链路**：`后端 Result.fail(500, "具体原因") → Axios HTTP 200 + body {code:500, msg:"具体原因"} → 拦截器判断 code≠200 → Promise.reject(Error) → catch 块读取 error.message`。但注意：如果后端抛出 RuntimeException（未被catch），Spring Boot 返回 HTTP 500 + JSON body，此时 `error.response.data` 才是后端的错误信息。

## 第十阶段：路径调整 400 Bad Request 修复

### 问题描述
路径调整页面点击"提交调整请求"后，控制台报错：
```
PUT http://localhost:8080/learning-path/1/adjust 400 (Bad Request)
[PathAdjust] 调整失败详情: Error: Request failed with status code 400
```
用户只看到"Request failed with status code 400"，看不到后端的具体原因。

### 排查过程

**根因1：`AdjustPathVO.reason` 的 `@NotBlank` 验证**
```java
@NotBlank(message = "调整原因不能为空")
private String reason;
```
前端虽然会自动生成 `reason`，但在某些边界情况下（如用户清空输入框后直接提交），如果 `reason` 传到后端为空字符串，Spring Boot 的 `@Valid` 验证会拦截，返回 400。

**根因2（关键）：Axios 拦截器不处理 400 错误的具体信息**

这是最关键的问题。Axios 的响应拦截器有两个回调：
```javascript
request.interceptors.response.use(
  (response) => { /* 只对 2xx 状态码生效 */ },
  (error) => { /* 对所有非 2xx 状态码生效 */ }
)
```

Spring Boot 返回 400 验证错误时，响应体是：
```json
{
  "timestamp": "2026-05-30T01:54:44",
  "status": 400,
  "error": "Bad Request",
  "message": "调整原因不能为空",
  "path": "/learning-path/1/adjust"
}
```

但旧的 error 拦截器对 400 走的是 `default` 分支：
```javascript
default:
  ElMessage.error(error.message || '请求失败')  // Axios 的默认消息 "Request failed with status code 400"
```
`error.message` 是 Axios 自动生成的，不包含后端的具体错误信息。后端的 `message` 字段在 `error.response.data.message` 中，但代码没有读取它。

### 解决方案

**修复1：去掉 `reason` 的 `@NotBlank`**
```java
// 改前：@NotBlank(message = "调整原因不能为空")
// 改后：移除注解，reason 可为空（前端自动生成兜底值）
private String reason;
```

**修复2：Axios error 拦截器读取后端响应体**
```javascript
// 改前：default: ElMessage.error(error.message)
// 改后：对 400/404/500 都读取 data.msg 或 data.message
case 400: {
  const msg = data.message || data.msg || data.error || '请求参数错误'
  ElMessage.error(msg)  // 显示后端的具体验证错误，如"调整原因不能为空"
  break
}
```

**修复3：PathAdjustView 的 catch 块去重**
由于拦截器已经 `ElMessage.error(msg)`，catch 块不应再显示一次，改为只 `console.error` 记录日志。

### 涉及的知识点

**Axios 拦截器的两个回调**：
- `response` 回调：仅在 HTTP 状态码为 2xx 时触发
- `error` 回调：在所有非 2xx 状态码时触发（400、401、403、404、500 等）
- 因此，处理后端错误必须在 `error` 回调中读取 `error.response.data`

**Spring Boot 验证错误的响应格式**：
- `@Valid` 验证失败时，Spring Boot 返回 HTTP 400 + JSON body
- body 包含 `message`（验证错误描述）、`status`（400）、`error`（"Bad Request"）
- 需要在前端 error 拦截器中提取 `data.message` 才能看到具体哪个字段验证失败

**`@NotBlank` vs `@NotNull` 的区别**：
- `@NotNull`：不能为 null
- `@NotBlank`：不能为 null、不能为""、不能为纯空格"   "
- 对于可选字段（有前端兜底值），去掉验证注解更灵活

## 第十一阶段：路径调整提交失败修复（res.message → res.msg）

### 问题描述
用户在路径调整页面点击"提交调整请求"后，显示"提交失败"，后端日志可以看到具体的错误原因，但前端页面只显示"请求失败"，看不到后端返回的具体错误信息。

### 排查过程

**根因：Axios 响应拦截器字段名不匹配**

后端 `Result` 类使用 `msg` 作为消息字段：
```java
public class Result<T> {
    private Integer code;
    private String msg;      // ← 字段名是 msg
    private T data;
}
```

但前端 `request.js` 的响应拦截器中读取的是 `res.message`：
```javascript
// 错误代码：res.message 始终为 undefined
if (res.code && res.code !== 200 && res.code !== 0) {
    ElMessage.error(res.message || '请求失败')  // ← BUG: Result 用的是 msg，不是 message
    return Promise.reject(new Error(res.message || '请求失败'))
}
```

**数据流向分析**：
```
后端返回 Result.fail(500, "路径调整失败: AI服务调用失败")
    ↓ HTTP 200 + Body: {code: 500, msg: "路径调整失败: AI服务调用失败"}
Axios 拦截器 response 回调触发（HTTP 200 = 2xx）
    ↓ res = {code: 500, msg: "路径调整失败: AI服务调用失败"}
判断 res.code !== 200 → true
    ↓ res.message 为 undefined
显示 "请求失败" ← 用户看不到真正的错误原因
```

**为什么用户看不到后端的具体错误**：
1. 后端用 `Result.fail(500, "具体错误信息")` 返回，消息字段是 `msg`
2. 前端拦截器读 `res.message`，但 Result 类没有 `message` 字段
3. `res.message` 始终为 `undefined`，降级显示"请求失败"
4. 用户只知道失败了，不知道为什么失败

### 解决方案

**修复1：前端 Axios 拦截器字段名修正**

`Media-edu/MediCraft-web/src/api/request.js` 第45行和第54行：
```javascript
// 改前：
ElMessage.error(res.message || '请求失败')
return Promise.reject(new Error(res.message || '请求失败'))

// 改后：
ElMessage.error(res.msg || '请求失败')
return Promise.reject(new Error(res.msg || '请求失败'))
```

**修复2：后端 improve error handling**

`dm/educate-server/.../LearningPathServiceImpl.java` 的 `adjustPath()` 方法：
```java
// 改前：JSON 解析失败时静默忽略
} catch (Exception ignored) { }

// 改后：返回具体错误信息
} catch (Exception e) {
    log.error("路径调整参数JSON解析失败, pathId={}, params={}", pathId, vo.getParams(), e);
    return Result.fail(400, "调整参数格式错误，请检查参数");
}

// 改前：所有异常统一返回模糊信息
} catch (Exception e) {
    log.error("路径调整失败", e);
    return Result.fail(500, "路径调整失败，请稍后重试");
}

// 改后：区分业务异常和未知异常，返回具体原因
} catch (RuntimeException e) {
    log.error("路径调整业务异常, pathId={}, type={}: {}", pathId, vo.getAdjustmentType(), e.getMessage(), e);
    return Result.fail(500, e.getMessage());
} catch (Exception e) {
    log.error("路径调整未知异常, pathId={}, type={}", pathId, vo.getAdjustmentType(), e);
    return Result.fail(500, "路径调整失败: " + e.getMessage());
}
```

**修复3：AI 服务调用增加明确异常处理**

`regenerateUnfinishedSteps()` 方法中增加 AI 调用异常捕获：
```java
// 改前：AI 调用失败直接抛异常，前端只看到 "请求失败"
String reply = chatClient.prompt().user(aiPrompt).call().content();

// 改后：捕获 AI 异常，给出明确提示
try {
    reply = chatClient.prompt().user(aiPrompt).call().content();
} catch (Exception e) {
    log.error("AI服务调用失败, pathId={}: {}", pathId, e.getMessage(), e);
    throw new RuntimeException("AI服务调用失败，请确认AI服务已正确配置: " + e.getMessage(), e);
}
```

### 改进步骤
1. 修改 `request.js`：将 `res.message` 改为 `res.msg`（第45行、第54行）
2. 修改 `LearningPathServiceImpl.adjustPath()`：JSON 解析失败时返回具体错误
3. 修改 `LearningPathServiceImpl.adjustPath()`：区分 RuntimeException 和未知异常
4. 修改 `LearningPathServiceImpl.regenerateUnfinishedSteps()`：AI 调用增加异常捕获

### 涉及的功能
- **路径调整模块**：延长周期、压缩周期、调整顺序、新增内容、简化内容
- **Axios 响应拦截器**：统一的响应/错误处理
- **后端 AI 服务**：DashScope ChatClient 调用
- **Spring Boot 参数验证**：`@Valid` + `@NotBlank`

### 涉及的知识点
**前后端字段名一致性**：后端 `Result` 类定义了 `code/msg/data` 三个字段，前端必须使用完全一致的字段名来读取。`message` 是 HTTP 协议层面的字段名，`msg` 是自定义 Result 类的字段名，两者不能混用。

**错误信息透传链路**：`后端异常 → catch → Result.fail(500, "具体原因") → HTTP 200 + body {code:500, msg:"具体原因"} → Axios response 拦截器 → 读 res.msg → ElMessage.error(msg) → 用户看到具体原因`。任何一环断裂（如字段名不匹配），用户就只能看到兜底文案。

**AI 服务的异常处理**：Spring AI 的 `ChatClient.call()` 可能因网络超时、API Key 无效、DashScope 服务不可用等原因抛出异常。必须在调用处捕获并转换为用户友好的错误信息，不能让原始异常直接穿透到前端。
